## Measured against the swift-markdown baseline (ask diary 2026-10-25-01)

`Benchmarks/MarkdownBench`, release, 19,897 assistant messages (12.4 MB) from the owner's session logs (not committed), load average 6.9, medians of five rounds.

| | swift-markdown (cmark-gfm) | AemiMarkdown | |
|---|---|---|---|
| Throughput, whole messages | 10.3 MB/s | **110 to 113 MB/s** (p10 to p90 0.108 to 0.117 s) | 11x |
| One message, p50 / p95 / p99 | 8.8 / 243 / 796 µs | 1.9 / 24.9 / 73 µs | 4.6x, 10x, 11x |
| Allocations per KB of input | 270 | **43** | 6x fewer |
| Allocations per message, p50 / p95 / max | 46 / 570 / 6,563 | 16 / 59 / 218 | |
| Stream 100 KB of real answers in 40-byte deltas | 4.94 s (reparse each delta); p50 1.7 ms, p99 4.5 ms | **0.010 s**, append and snapshot each; p50 3.2 µs, p99 11.9 µs | about 500x |
| Allocations per delta (real answers) | not measured | p50 10, p95 11 | does not grow with the answer |
| Stream one 100 KB paragraph | not measured | 0.75 s; p50 261 µs, p95 534 µs per delta | cost is the open paragraph, as designed |
| Stream one 100 KB code block | not measured | 0.002 s; p50 0.7 µs, 4 allocations per delta | O(delta) |

What the numbers do not say: the baseline ran the same way (parse only, release, the same kind of corpus, one machine), but the two were not interleaved in one process, so the ratio carries the spread of two runs; the parse includes tables, strikethrough and autolinks, as shipped. The throughput is not the SIMD ceiling: plain text is skipped byte by byte through a table, and a set scan (Aemi's kernels, roadmap 0065) is the next measured change.

## GitHub conformance and speed (later the same day)

- Every extension chapter of the GFM spec passes (30 examples; ratchet empty): task lists, tag filter (renderer only), footnotes with multiple backrefs. `![^1]` keeps the `!` as text.
- Alerts and math have no reference implementation; their tests state GitHub's documented rules. `.gfm` is the specified set, `.github` adds both.
- Math: a failed search for a closer is remembered per kind (`$`, `$$`) and each search is charged to the work budget. Without it `$a$ $` repeated was quadratic (1.2 M steps at n=1000, ×4 per doubling): the robustness test caught it once its unit list included math.
- Speed (CPU time, 12.4 MB corpus, loaded machine, median of runs): blocks and inlines 0.053 s (235 MB/s) with a reused parser; blocks only 0.030 s. Unchanged by the extensions.
- Open: a 100 KB single paragraph still costs ~240 µs per delta.

## Mistakes and corrections

- `open(path, "w").write(open(path).read()...)` once emptied a source file in the Aemi work; here edits are read first, then written.
- The first autolink scheme and attribute mutations were not caught by the differential test: its generator could not produce them. A test that passes under mutation proves nothing, so the generator was widened until it failed.
- A commit went in with a red suite (the stale ratchet), because the commit hook runs format and lint and not the tests. It was amended in the same minute. The pre-push hook is the one that runs the suite.

## Owed

- A remote for AemiRegex, and for this repository (neither exists), so the dev tests and ask's pin can resolve by URL.
- Allocation floor: 43 per KB is not near zero. Where they come from has not been profiled (candidates: the source copy of `parse(_:)`, per-leaf arrays, the tape growth).
- The set-scan kernel and SIMD skipping of plain text; incremental inline parsing of the open leaf (a 100 KB paragraph costs O(paragraph) per delta).
- Doc comments on the public surface are brief; DocC is not built.
- Static analysers (deadwood, dolly, arcleak) are not wired in; CI does not exist.
